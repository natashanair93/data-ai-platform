Console state reference

Every state the test console takes, in one sheet — the morphing composer from 1a plus the ask-first journey from 3a. One shell, three groups of states: which trigger fires the agent, the questions asked before a partial test can run, and the source the input finally comes from.

THE SHELL — CONSTANT IN EVERY STATE
1 · Scope strip — what is being tested + exit 2 · Transcript — runs, answers, receipts 3 · Console slot — BACK · title · body · footer 4 · Footer — Test ⌄ left, RUN right
Only the console slot changes. Nothing else moves between states — no state relocates RUN, and no state leaves a bare greyed field.

Testing one step of the agent on 1a's morphing composer. 2a answers both questions as a storyboard: source options appear as pills above the input, and the input slot morphs per source — the text field only greys out in the one state where typing is genuinely meaningless. 2b is the alternative: a persistent source dropdown in the footer, no pills.

Test trigger composer — UX options

The Test chat panel must work for every trigger (chat, manual, scheduled, event) and every input source (typed, pinned data, last run, upstream agent). Three patterns below — 1a keeps the composer as the single run surface and morphs its input slot; 1b stacks a trigger console above an unchanged chat composer; 1c treats every trigger as a message. 1d shows the input-source states applied to the recommended pattern.

1a Morphing composer RECOMMENDED

One composer card, always in the same place.
