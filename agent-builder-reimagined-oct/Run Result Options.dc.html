Run result — three sketches
Every run, whatever its scope, has to answer four questions in a 420px panel: did it work, what did it cost, is it safe, what now. Each option is shown at true width in both pass and failure. Reference ids: 1a · 1b · 1c.
1 · FUNCTIONAL Passed, or failed and where. Same card shape either way.
2 · COST + LATENCY Two numbers, always in the same place.
3 · KEY EVALS Bias + Toxicity by default, extensible.
4 · ONE NEXT STEP Optimize · Build · See details. Rest in a kebab.

Four labelled bands in a fixed order, so your eye learns one path and reuses it on every run. Failure keeps the identical shape and inserts a red reason band — nothing moves, evals go to NOT RUN rather than disappearing.
Cost: tallest of the three (~330px), and it reads like a report rather than a reply — heavy if you run ten tests in a row.

Same result card, different way back. A scheduled trigger has no message to type, so the composer stays as the trigger console it already is — schedule line, config data, TEST. The card doesn't change shape between triggers; only the footer does.
My pick: 1b
You'll see this card after every single run, including ten in a row while iterating — so its resting size matters more than its completeness. 1b answers all four questions in ~155px by letting color carry the eval verdicts instead of a table, and it keeps the panel feeling like a conversation rather than a monitoring dashboard. 1a is the one to pick if you'd rather every number be explicitly labelled; 1c only holds up while there are exactly two evals.
Two things I'd flag before building: OPTIMIZE as primary on a passing run is an odd default — it invites churn on something that just worked. Consider primary = SEE DETAILS on pass, OPTIMIZE on fail. And "nothing broke" is not the same claim as "the output is right"; the functional check is honest only if the card avoids implying correctness, which is why 1b says "Passed" rather than "Success".
