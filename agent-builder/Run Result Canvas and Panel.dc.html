Canvas + panel, output types, and the failure model
Your question about downstream has a sharper answer than yes, and it changes the whole design. Research below, then options. Canvas + panel: 3a · 3b · 3c. Output types: 4a · 4b · 4c · 4d.
Finding 1 — a green trace is not a good answer
The failure mode every observability vendor warns about: an agent runs eighteen steps, calls the same search tool six times, never finds the file, and reports success. Every span returns 200, latency is normal, token use is unremarkable — the dashboard shows a healthy agent while the product is broken. Structural tracing cannot see semantic failure.
So your requirement 1 ("nothing breaks") and requirement 3 ("evals") are two independent verdicts, and the card has to be able to say ran fine, quality failed. One combined status light would be a lie in exactly the case that matters most.

Finding 2 — your downstream question: yes for crashes, no for bad output
Two different propagation behaviors, and conflating them is the trap:
HARD STOP Tool 403s, model errors, schema mismatch. Execution halts. Downstream agents never ran — they are not failed, and painting them red blames the wrong agent. They need a third state: blocked.
SOFT DRIFT An intent step returns "billing inquiry" when the customer asked about cancellation. Every downstream step — retrieval, generation, tool selection — follows that wrong signal faithfully and returns green. Downstream did run, and its output is worthless. When the final answer is wrong, the root cause is usually a misleading intermediate several steps earlier.
Design consequence: the canvas must be able to mark a node green-but-suspect and propagate an amber "downstream of a problem" state, not just a red stop. And the panel should name the first bad step, never the last one to run.
Finding 3 — five node states, and edges carry state too
Per-node execution state on a canvas is a known primitive — running, succeeded, failed, skipped — and it needs edge-state propagation, not just node badges. Adding the soft-drift case gives five. One caution: greying-out already means "disabled by the user" in most builders, so blocked can't rely on dimming alone; it carries a label.

What I'd build
Split the verdict in two. "Ran" and "Quality" are separate lines of evidence. Three headline states: Passed · Ran, quality failed · Failed. This is the single most important change and it's cheap. Five node states with edge propagation. Ran ok · soft (eval failed) · failed · blocked · out of scope. Blocked gets a NEVER RAN label, not just dimming, because dimming already means "disabled" to anyone who's used a workflow builder. Canvas = where, panel = what. Per-node latency and cost live on the nodes; run totals, evals, output and actions live in the card. Bidirectional selection: clicking a node scopes the panel, clicking an agent name in the panel selects the node. Point at the first bad step. Both failure modes name the earliest problem, not the last thing to run, because in a chain the root cause is almost always upstream of the symptom. RERUN FROM HERE on the canvas. Replaying from a checkpoint instead of the top is the highest-leverage affordance in the whole flow once chains get slow. Output block switches on declared type. Text · file · structured · action-only. Test-mode side effects must be labelled as simulated.
Two things I'd push back on
OPTIMIZE as primary on a passing run invites churn on something that just worked, and on a failed run it's arguably wrong too — a 403 credential error isn't an optimization problem, it's a fix. Consider: pass → SEE DETAILS primary; soft fail → OPTIMIZE primary; hard fail → FIX primary (deep-links to the broken tool config).
Bias and toxicity are weak defaults for most of these agents. They're safety floors, and they'll read green forever on a feedback classifier while it quietly misroutes tickets. The eval that would actually catch failure here is task-specific — did it use only the provided fields, did every recommendation cite a source. Worth defaulting to one task eval alongside the two safety ones.
