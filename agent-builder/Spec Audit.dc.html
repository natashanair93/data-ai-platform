Spec audit — seven specs against Fusion Agent Studio v4
Read against the v4 source, not from memory. Headline: v4 already covers most of 01 and 02, and contains working seeds of 03 and 04 that the specs don't credit it for. The real gaps are structural — spans, per-node attribution, edge data, and the two library surfaces. Four requirements actively contradict what's built, and one of them is a vocabulary collision that will cause bugs if we don't settle it first.
Spec 07 is the sharpest thing in the pack, and it reframes the audit: a missing surface is not automatically a gap. What matters is whether each of the five questions can be answered. v4 answers stage 1 well, stage 2 shallowly, and stages 3–5 barely — so I've scored the journey separately at the bottom, and it drives the sequencing more than the per-spec counts do.

Four conflicts — settle these before building anything
Each one is a decision, not a bug. Ordered by how much downstream work they block.
C1 · BLOCKS ALL
"Baseline" means two different things
v4 ships "BASELINE EVALS" — toxicity + bias, free, automatic on every full run, async-filling chips. In the specs, Baseline is a pinned SuiteRun that all deltas compute against (foundation §2, R3), and toxicity/bias are the safety pack (D3). Same word, unrelated concepts, both about to appear on the same screen.
Recommend: rename v4's to Safety pack and reserve "baseline" exclusively for the pinned SuiteRun. Cheap now, expensive after 03 and 04 ship copy referencing both.
C2 · BLOCKS 01
v4 locks the canvas in test mode; spec 01 needs it editable
v4 hides the terminal +, collapses the left panel and drops node slots when testing — deliberate, and we designed it that way. But 01's founding principle is "the editing picture and the trace picture are the same picture," and req 10 says any edit immediately marks the overlay stale — which presumes you can edit while results are on screen.
Recommend: keep the lock during execution only, and unlock once results land. The stale treatment (req 10) then becomes the mechanism that makes editing-with-results safe — it's the reason 01 can afford to allow it. Also resolves the awkwardness that today you must leave test mode to act on what a test told you.
C3 · BLOCKS 04
v4's comparison is a chat message; the spec needs a durable record
v4's Optimize drafts a candidate, auto-runs the test set and posts a comparison card into the transcript (quality / avg cost / avg latency, winner flags, verdict "Matches quality at 48% lower cost"). Spec 04 req 17 wants the opposite: "an experiment is a durable record of why a version was chosen," browsable as history.
Recommend: keep the chat card as the notification (it's a great J1 moment — the result arrives where the user asked for it) and make it a link into a persisted Experiment. Don't delete it; back it with an entity.
C4 · TENSION
v4 withholds eval readouts from partial runs
v4 says plainly: "Baseline evals run on full-system tests only — this was a partial run." D1 says one execution produces all four readouts and J4 says never gate the inner loop on outer-loop rigor. Scoped runs are the stage-1 behavior, so they're the runs least able to afford a blank.
Recommend: partly defensible — safety can't score an output that doesn't exist yet. But functionality and cost/latency absolutely apply to a node run, and today they're bundled into the same withholding. Split the four dimensions so each says either a value or a specific reason, never a silent nothing.

The journey test — can each question be answered today?
This is the score that should drive sequencing. v4 is excellent at the inner loop and thin everywhere the confidence ratchet turns.
STAGE 1 · SERVED "Does this even work?" Scoped + full runs, live node states, replies in seconds. This is v4's home turf. Missing only cost on the readout.
STAGE 2 · SHALLOW "Why did it do that?" You can see that a node failed, not why. No rendered prompt, no payloads, no evidence. The detective can't descend.
STAGE 3 · BLOCKED "Or did I get lucky?" Cases can be saved but never seen, listed or run as a set. No pass-rate, no baseline. The hardest transition has no destination.
STAGE 4 · FAKED "Better, cheaper, faster?" Optimize works end-to-end and is genuinely good — but on an invisible test set, with no insights to trigger it from felt pain.
STAGE 5 · ABSENT "Trust it enough to ship?" A publish gate exists but assembles no evidence. Nothing to review, no safety block, no baseline comparison.
Journey requirements J1–J6
J1 offered at moments — mostly HAVE. v4 is already good here and the specs should learn from it: post-run action chips, FIX WITH AI on the failing node, "save last test as case", the stale banner offering replay. These are textbook J1 instances that predate the spec. J2 the question travels — MISSING. The one deep link that exists (run → results) opens the workspace unfocused. Every other number is inert. This is the single biggest structural gap and it's a prerequisite for 03 being worth building. J3 rigor accumulates — PARTIAL. Capture exists; accrual is invisible. Saving a case today feels like it goes nowhere, which is exactly the failure J3 warns about. J4 never gate the inner loop — AT RISK. See C4. One withheld readout on the most common run type. J5 each cycle ends richer — PARTIAL. There is one nice instance: "vs. last full run — no regressions, duration 6.2s → 5.8s". Extend that pattern rather than inventing a new one. J6 stage skips legitimate — HAVE. Nothing in v4 assumes prior stages. Preserve this when adding gates.
Recommended split — and where I'd deviate from the pack's build order
The pack says build 03 first because it settles vocabulary. I agree with the reasoning and disagree with the conclusion: the vocabulary that needs settling isn't Run Detail's, it's the readout contract — R1's four chips, the node states, and the words we use for safety vs. baseline. That's ~a day of work inside surfaces that already exist, and every other spec consumes it. Build it first or every later surface will be re-copyedited.
SPRINT 0
The readout contract — no new surface
Settle C1 (rename to safety pack) and C4 (split the four dimensions). Land R1's four chips and the five node states in the existing run card and canvas — most of this is already sketched in Run Result Canvas and Panel. Add cost. Nothing here needs a new screen, and it makes 01–06 speak one language.
SPRINT 1
03 Run Detail + the deep-link contract (J2)
Sketch together because they're one thing: the surface is worthless without focused entry, and the contract has nowhere to land without the surface. This unblocks stage 2, the worst-served real question. Heaviest sprint — expect two sketch rounds.
SPRINT 2
01 Canvas — edges, badges, insights
Pairs with 03: EdgeRecords and spans are the same data seen spatially. Resolve C2 here. Insights (R6) are the trigger for stage 4, so they must exist before 04 is meaningful.
SPRINT 3
05 Suites + 02 capture polish
Deliberately together, and earlier than the pack suggests. 05 is thin, and it's the destination that makes v4's existing capture affordances stop feeling like dead ends — the cheapest possible fix for the journey's hardest transition (stage 3). Building 04 before this would mean an Experiments surface with no suite to run.
SPRINT 4
04 Experiments — upgrade the seed, don't replace it
Resolve C3. v4's comparison card and promote flow are a real head start; the work is the scorecard, the optimizer job config with eval gating, and per-case diff.
SPRINT 5
06 Eval Registry + safety pack admin
Last on purpose. Until quality scores are visible in 03 and 04, an evaluator library has nothing to explain. Its trust argument only lands once the user has seen a score they distrust.
One thing the pack under-specifies
D1 says four dimensions, but the research on multi-step agents says the dangerous case is ran clean, output wrong — every span green while the product is broken. "Functionality ✓ + Quality ✗" technically expresses it, yet in the chat panel quality is on-demand (D2), so the default readout for that run is all-green with a dash. The most dangerous state in the product is its quietest one. Worth deciding in Sprint 0 whether the chat panel needs a cheap always-on quality signal, even a weak one, rather than a dash.
